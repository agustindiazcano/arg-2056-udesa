## 2. Parity (design section 7, in this order of importance)

1. **Hand-computed minimal cases per mechanism**, the same ones as the Python tests (for example one year of capital accumulation: `K = 100`, `delta = 0.05`, `s = 0.2`, `Y = 50` gives `K' = 105`). These prove correctness.
2. **Property tests**: cohort conservation; constant returns to scale (scaling `K` and `L` by `k` scales `Y_core` by `k`); monotone response of output to `A`; the identities (`gdp_per_capita = GDP / population`, the HDI formula).
3. **Golden vectors generated by Python, only in addition to (1) and (2)**: they prove stability, not correctness. Tolerance `1e-9` relative for the deterministic functions, stated per function. A test regenerates the vectors with `gen_parity.py` into a temporary directory and compares with the committed file, so an equation change without regenerating fails.
4. The invalid-input messages match Python's byte for byte for the functions already covered by `population_invalid.json`; extend that file to the new functions.

## 3. The sandbox wiring

Only the parameters section 6 of the design says the sandbox exposes (`gro.s`, `gro.gA`, `pop.tfr_target`, `pop.mig_rate`, `ai.delta` with the overlay on or off and the range position, and the growth rate of the rule-of-70 explainer), within the bounds of `params.json`. Parameters without a value use the median of their range and the sandbox says so in its assumptions text. The sandbox keeps its existing comparison with the model range and its table views. Every slider change recomputes the expected path (the existing selectors and chart builders consume it unchanged); an e2e test moves a slider and checks the chart's data changed.

If section 6 has been refined by `sensitivity` (the measured ranking), follow the report; if it contradicts the design, stop and tell me.
