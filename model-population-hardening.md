# Task: `model-population-hardening`

Branch: `task/model-population-hardening`. One PR. Read `AGENTS.md`, `LASTCONTEXT.md`, `PENDING.md`, `docs/audits/main.md` (findings F5, F8 and F9 are the reason for this task), `docs/model-design.md` section 2.1 and decision `D-pop-1`, `docs/decisions.md`, `model/src/argmodel/population/cohort.py`, `web/src/model-ts/population.ts`, `model/tests/test_population.py`, `web/tests/parity/population.test.ts`, `model/parity/gen_parity.py` and `model/parity/population_parity.json` first.
Prerequisite: none (the cohort step and its TypeScript port are already merged).

## Goal

Make the cohort step safe to build on. The equations do not change; what changes is that wrong inputs fail loudly with the same message in Python and in TypeScript, that a hidden bug the audit found by mutation (`migration[0]` never tested) is covered, and that the two implementations are tested against hand-computed values and not only against each other.

Strict TDD: every behavior below starts as a failing test. Atomic commits. Before every push run `python scripts/precheck.py`.

## Out of scope (do NOT do)

- Do not change the equations of `step_population` or `project_population`, their signatures or their return values for valid input.
- No new dependency. No new feature (no fertility or mortality drivers: that is `model-population-drivers`). No UI.
- Do not edit `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` or `docs/model-design.md`. Do not fake CI. Do not silence any checker.

## 1. Validation (same rules and the same message text in both languages)

Python raises `ValueError`; TypeScript throws `Error`. The text is identical, copied from this list (the argument names are the Python ones in both languages, so the messages match byte for byte):

| Condition | Message |
|---|---|
| fewer than 2 age groups (`F8`) | `step_population needs at least 2 age groups, got {A}` |
| `survival`, `fertility` or `migration` length differs from `n_t` (`F9`) | `step_population: {name} has length {L}, expected {A}` |
| any input contains `NaN` or an infinite value | `step_population: {name} contains a value that is not finite` |
| `survival` outside [0, 1] | `step_population: survival must be between 0 and 1` |
| `fertility` negative | `step_population: fertility must not be negative` |
| `n_t` negative | `step_population: n_t must not be negative` |
| the result has a negative cohort (`D-pop-1`, option "raise") | `step_population: negative population in age group {i}: {value}` |

For `project_population`: `project_population: {name} must have shape ({T}, {A}), got ({rows}, {cols})` when `survival`, `fertility` or `migration` is not `(T, A)` with `A = len(n_t0)`; and the errors of the step are raised with the year added: `project_population: year {t}: <step message>` (`t` is the 0-based index of the step).

Decision `D-pop-1`: the design recommends **raise** on a negative cohort. This task implements raise. If the human chose clamp, they say so before the task starts; do not clamp silently.

## 2. Tests that must exist

Python (`model/tests/test_population.py`) and TypeScript (`web/tests/parity/population.test.ts` or a new file next to it):
- Each row of the table above: one test with the exact message, and the positive case (valid input still returns the same array as before).
- **Non-zero `migration[0]`** (audit F5, mutation M1 survived): a hand-computed case. Example: `n_t = [10, 20, 30]`, `survival = [0.5, 0.5, 0.5]`, `fertility = [0, 0.1, 0.1]`, `migration = [4, 0, 0]`: births `= 20*0.1 + 30*0.1 = 5`, so `n_next[0] = 5 + 4 = 9`; `n_next[1] = 10*0.5 = 5`; `n_next[2] = 20*0.5 + 30*0.5 = 25`. Write the arithmetic in a comment.
- A hand-computed case for each age term separately (births, ageing, open interval, migration at each age) so that each line of the step is covered by a value that does not come from the code under test.
- **Conservation** (criterion C5 of the design): `sum(n_next) = births + survivors + migration` for several random-looking but fixed inputs, to a tolerance of `1e-9` relative.
- **The golden file is read by Python** (audit F5): a test loads `model/parity/population_parity.json`, runs the Python code on its inputs and compares with its stored outputs. A second test asserts that the file is what `gen_parity.py` produces now (so a change to the equations without regenerating fails).
- **Two ages** (`A = 2`) is accepted by both languages and gives the same result; `A = 1` and `A = 0` are rejected by both (`F8`).
- TypeScript and Python agree on every row of the validation table: a test in TypeScript reads a small JSON list of invalid cases (generated by `gen_parity.py` into `model/parity/population_invalid.json`, with the expected message) and checks the thrown message for each; the Python test reads the same file.

## 3. Changes in the code
