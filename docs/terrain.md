# Terrain

The Andes scene needs terrain. This tool bakes it from **measured elevation only** (a digital elevation model, DEM) into small static files. Nothing is generated by a model and nothing is fetched from a tile server at runtime.

Decision: terrain is baked from measured data. Any procedural detail added later (in `andes-integration`) must be labeled as illustrative in the UI and in the references page.

This repository contains the tool, not terrain output. The human downloads the DEM, registers it, runs the tool and commits the outputs.

## 1. Choosing bounding boxes

The bounding boxes are a human decision. `terrain/config.example.json` only shows the shape, with obviously fake values (`fake_dem_dataset_replace_me`, `fake_region_replace_me`, a 1 degree box at 0, 0). Do not use it as is.

Recommended method: take the minimum and maximum `lon` and `lat` of the events in the Andes facts dataset (`data/schemas/andes_events.schema.json`: fields `lat`, `lon`, `elevation_m`) and add a margin. A box is `[west, south, east, north]` in decimal degrees (west < east, south < north).

The tool crops to the box **snapping outward to whole pixels**, so the box in the metadata (`bbox`) can be slightly larger than the requested one. The requested box must be fully covered by the DEM tiles, or the region fails and prints the uncovered fraction.

## 2. DEM sources (leads to verify, not facts)

These are candidates only. Check the current license or terms, the vertical datum, the resolution and the redistribution rules on the publisher's page before using any of them, and record what you found in the manifest.

| Lead | To check |
|---|---|
| Copernicus GLO-30 | license and attribution wording, tile format, vertical datum |
| SRTM 1 arc-second | terms of use, void handling, tile naming |
| National elevation models (for example from the national geographic institute) | availability, license, resolution, whether redistribution is allowed |

The manifest fields `source`, `source_url`, `retrieved_at` and `license_or_terms` are copied into the metadata of every output.

## 3. Register the DEM files

Put the GeoTIFF tiles under `data/raw/<dem_dataset_id>/` and register every file with the data-pipeline manifest (see `docs/data-pipeline.md`):

```
python -m datapipe register <dem_dataset_id> <tile.tif> --source "..." --source-url "..." --retrieved-at YYYY-MM-DD --license "..."
```

Run it with `scripts` on the Python path (`PYTHONPATH=scripts` in bash, `$env:PYTHONPATH = "scripts"` in PowerShell). All tiles of the dataset must carry the same `source`, `source_url`, `retrieved_at` and `license_or_terms`, otherwise the tool fails. Every file is verified (hash, no unregistered files) before anything is read.

Requirements: the tiles must be GeoTIFF in EPSG:4326, north-up, with the same pixel size and aligned to the same pixel grid.

## 4. Install and run

```
pip install -r scripts/terrain/requirements.txt
PYTHONPATH=scripts python -m terrain bake --config terrain/config.json --attribution "<attribution text>"
PYTHONPATH=scripts python -m terrain verify --meta web/public/terrain/<id>.json --points points.json
```

`bake` options: `--raw-root` (default `data/raw`), `--out-root` (default `web/public/terrain`). Exit codes: 0 success, 1 any validation or processing error (`ERROR <region> <reason>` on stderr, `ERROR config <reason>` for an invalid config), 2 usage error. Each region is all-or-nothing: a failing region writes no file, and the other regions still run.

Outputs per region: `<id>.height.png` (terrarium RGB), `<id>.hillshade.png` (8-bit grayscale) and `<id>.json` (metadata, schema `data/schemas/terrain_meta.schema.json`). Running twice in the same environment gives identical bytes.

Local checks: `python scripts/precheck.py` runs the terrain tests when numpy, rasterio and Pillow are installed, and otherwise prints exactly `SKIP terrain: install scripts/terrain/requirements.txt` and goes on. CI always runs them (job `terrain`).

## 5. Compare baked heights with the Andes facts

`points.json` is `[{ "name": "...", "lon": 0.0, "lat": 0.0, "expected_m": 0.0 }]`, built by the human from the events of the Andes facts that have a non-null `elevation_m`. `verify` prints a tab-separated table:

```
name	expected_m	baked_m	difference_m
```

The baked value is a bilinear sample at the point. A point outside the box, or within half a pixel of its edge (where four pixel centers are not available), prints `outside bbox` instead of a number. `verify` exits 0 whenever it ran and never judges: a difference is expected, because a historical elevation, a pixel average and a point sample are different quantities, and the human decides what is acceptable.

## 6. Processing rules (as implemented)

1. Mosaic of the registered tiles. Overlapping valid pixels that differ by more than 1 m fail (first location printed); otherwise they are averaged.
2. Crop to the box; the box must be fully covered.
3. Nodata: the declared nodata value only. More than 0.1% of the pixels in the box fails (count and first locations printed); otherwise each is filled with the nearest valid pixel (ties: smallest row, then smallest column) and `filled_fraction` is recorded. Elevation 0 is a valid measurement.
4. Resample so the long side is `max_size`, by area-weighted block averaging. Never upscales.
5. Encode as terrarium: `value = height_m + 32768`, `R = floor(value / 256)`, `G = floor(value) % 256`, `B = floor(frac(value) * 256)`, heights rounded to the nearest 1/256 m (ties to even). Heights outside -32768..32767 fail.
6. Hillshade by Horn's method from the baked heights. Ground distances use a spherical Earth of radius 6,371,008.8 m (a decision of this tool; the brief did not give one) and the row latitude for longitude. Border pixels use neighbours extrapolated linearly. Flat terrain gives `round(255 * sin(altitude))`.

## 7. Size budget and detail

`max_bytes_per_region` caps the two PNGs together; a region over the budget fails and writes nothing. The trade-off is `max_size` against bytes: more pixels mean more detail and larger files.

Ground size of a pixel, from the metadata:

- along latitude: `meters_per_pixel.y = pixel_size_deg.y * (pi * R / 180)`
- along longitude at latitude `phi`: `pixel_size_deg.x * (pi * R / 180) * cos(phi)`

with `R = 6,371,008.8 m`. Since the long side is `max_size` pixels, `pixel_size_deg` is about `box size in degrees / max_size`. The metadata stores `meters_per_pixel` at the center latitude of the box.

## 8. Attribution

`--attribution` is required and is copied into the metadata. Show the attribution text of the DEM publisher (as required by the license you verified) in the scene and add it to the references page.

## 9. In the web app

`web/src/terrain/` is renderer-agnostic: `loadTerrain(baseUrl, id)` returns `{ meta, heights }`, `sampleElevation(terrain, lon, lat)` returns meters or `null` outside the box (never 0), and the pixel convention is documented in `decode.ts` (pixel (0, 0) has its center at west + 0.5 pixel, north - 0.5 pixel).

## 10. The Andes scene and the made-up terrain

The Andes scene (`web/src/scenes/andes/`) loads `/terrain/andes` (so the region `id` in `terrain/config.json` must be `andes`). While that file does not exist it draws a made-up terrain (`web/src/terrain/synthetic.ts`: a deterministic cordillera around the events, source "Terreno sintético") and says so on the screen. Nothing else changes when the real files are committed. The attribution of the baked terrain is shown in the scene.
